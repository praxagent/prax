# AutoEnvScaling: Automating the Data Flywheel with Terminal Agents

**Verdict: document + adopt one honesty fix and one check; queue one
flywheel for #29; don't adopt the training.**
- **What it is.** A proposer agent, working in a sandbox, builds RL training
  tasks for terminal agents from the failures of the model being trained. A
  task is admitted only if:
  - its reference solution actually passes;
  - doing nothing fails;
  - the current model sometimes solves it.
- **The finding that transfers is about harnesses, not training.** Putting
  task generation inside an execute-and-repair harness raised the
  valid-environment rate from 39% to 86% on average, and from 3.5% to 89% for
  the weakest model. Running the reference solution during generation is most
  of that gain.
- **Adopt:**
  - **`plugin_write` should not say "sandbox test PASSED" when no tool was
    called.** Prax's plugin test imports the module and checks that
    `register()` returns named tools. That is the paper's "it builds" check,
    which it shows is far from "it works".
  - **Give plugins a behavioural admission check:** one example call that
    must succeed.
- **Queue for #29:** agent-written *case generators*, the flywheel half of
  #278's generated families. Admit them with the same checks, plus
  calibration against Prax and difficulty judged from outside the loop, as
  our [AutoBenchmark](autobenchmark.md) note requires.
- **Bank:**
  - training one role in shared weights eroded the other (second sighting,
    after [MASS](mass-multi-agent-self-supervision.md));
  - Ask-F1, not ask rate, is how to measure clarification;
  - the "one model improves itself" result began with distillation from
    three other models.

Source: Yu, Peng, Liu, Shi, Wang, Cheng, Wu, Yao, Jaques, Shi, Gao,
"AutoEnvScaling: Automating the Data Flywheel with Terminal Agents",
[arXiv 2610.14163](https://arxiv.org/abs/2610.14163) (October 2026).
Microsoft, with Northeastern, Stanford, UW and UNC.

## What it is

- **Environment design as a terminal task.** The proposer works in an
  isolated container with:
  - the solver's past rollouts and verifier outputs;
  - previous environments;
  - Harbor's `create-task` skill;
  - its own memory and tools;
  - restricted web access, with egress rules blocking benchmark pages.

  It writes a complete Harbor task (instruction, container, reference
  solution, tests), and builds and tests it in child containers. Each
  episode starts from an assignment: a parent task, with the solver's pass
  rate and most common failure. The proposer builds a simpler variant when
  the solver fails, and a harder one when it succeeds.
- **Admission runs outside the sandbox, where the proposer can't edit it:**
  - **validation:** the reference solution scores 1, an empty solution scores
    under 0.5, and no 13-gram overlap with Terminal-Bench;
  - **review:** a `harbor check` rubric review, graded by the proposer's own
    model;
  - **calibration:** the current solver's mean reward is in [0.25, 0.75],
    with spread ≥ 0.1 over 4–8 attempts.
- **The proposer's reward** is −1 for a broken task, −0.25 for a valid one
  that misses the band, and +1 for an admitted one.
- **Proposer improvement:**
  - a frontier proposer improves its harness between rounds (memory, skills,
    tools);
  - an open model plays both proposer and solver, and is trained on both
    rewards with DPPO.

## Results (as reported)

- **Generation (Table 2, eight proposers):**
  - valid-environment rate, averaged over models: prompt-only 39%, prompt
    with execution feedback 57%, the agent harness 86%;
  - the weakest model gains most: DeepSeek-V4-Flash 3.5% → 89.0%, GPT-5.6-luna
    17.2% → 83.5%;
  - cost per valid environment falls for six of eight models, by up to 75%.
  - **Executing the reference solution during generation** is most of the
    effect (Table 11): GPT-5.6-sol 19.5% → 84.8% with that self-check alone.
- **RL with frontier proposers (Table 3),** against a Tmax pool regenerated by
  the same proposer and trained for the same steps, on Terminal-Bench 2.1:
  - Qwen3.5-9B: 27.2 → 33.5 (GPT-5.6-sol as proposer) and 29.2 → 36.6
    (Claude Opus 5);
  - Qwen3.5-35B-A3B: 34.6 → 38.9 and 35.5 → 39.3.
  - **Without the solver's rollouts in the proposer's workspace,** the 35B
    gain shrinks to +0.7, or −2.9 with Claude Opus 5 as proposer.
- **Self-improvement:** Qwen3.6-35B-A3B in both roles.
  - Terminal-Bench 2.1: 41.1 → 53.3 (Tmax: 47.2).
  - Terminal-Bench 4.0: 1.6 → 3.2 (Tmax: 1.4).
  - Without training the proposer role, the solver's RL eroded the proposer:
    valid environments fell from 86.8% to 22.4%, and training collapsed
    (Appendix G.2).
- **Asking for help (HiL-Bench):** 500 generated underspecified tasks, each
  with a registry of withheld details.
  - Task success went 6.8% → 33.9% and Ask-F1 29.6% → 55.3%, against
    training on the 100 official tasks.
  - The ask rate barely moved (84% → 90%): the model learned to ask *the
    right* questions.

## What the paper says, read closely

- **The self-improvement run is not from zero.** The base model wrote valid
  environments 32% of the time, so it was first fine-tuned on 600 proposer
  trajectories from **Claude Opus 5, DeepSeek-V4-Flash and Kimi-K3**
  (Appendix H). "One model designs its own training environments" begins
  with distillation from three other models.
- **Verification is the weak joint, and the authors say so** (A.1):
  - the reference solution and the tests are written by the same proposer,
    so a shared mistake passes;
  - generated tests "can still miss incorrect solutions or reject valid
    ones";
  - the review rubric is graded by the proposer's own model;
  - decontamination is 13-gram text overlap, which "does not rule out
    paraphrased copies". The proposers are frontier models that may know
    Terminal-Bench tasks from pretraining.
- **A gap we see in their admission rule.** Calibration requires the solver's
  rewards to *vary* across attempts. A flaky or nondeterministic test meets
  that requirement for free. The proposer's skill tells it to avoid flaky
  tests, but nothing checks for flakiness, and the proposer is trained on a
  reward for passing calibration. Directives lose to rewards; the
  [harness-learning](harness-learning.md) composition experiments measured
  exactly that. Running the reference solution several times and requiring
  identical rewards would close it.
- **Terminal-Bench 4.0** moves from 1.6 to 3.2: a doubling in absolute
  points too small to read much into.
- **The evaluation harness is theirs** (the Pi agent, 4 CPUs, 8 GiB).
  Absolute scores sit well below model-card numbers: their own tests found
  the harness "accounts for most of this gap".

## Against Prax

| AutoEnvScaling | Prax |
|---|---|
| Admission: the reference passes, *and an empty solution fails* | `plugin_write` → `sandbox_test_plugin`: the module imports, `register()` exists, the tools have names and descriptions. **No tool is ever called.** The reply then says "Plugin written and sandbox test PASSED" |
| Generated tasks validated by execution, both ways | #278's `case_generators.py`: every generated case is tested both ways, with the correct answer passing and the slip failing, the answer recomputed from the prompt. The same rule, applied by hand |
| Calibration: the current solver sometimes succeeds | Not done. Our capability suite already fails the discrimination check ([eval hillclimbing](automating-eval-design-hillclimbing.md)) |
| Admission checks outside the proposer's reach | #29's scorer is fingerprinted and outside the editable surface: the same invariant |
| Solver rollouts guide what gets built next | #278's feedback set shows the proposer real failures. Nothing writes *new cases* from them yet |

## Adopt

### 1. Say what the plugin test checked

**The problem:** "Sandbox test PASSED" tells the model, and through it the
user, that the plugin works. The check behind it shows only that the module
imports and registers named tools. That is the paper's "it builds" level, and
its own numbers show the distance from there to "it runs correctly".

Our own Terminal-Bench sweep found 85% of scored failures *claimed* success
(the calibrated self-assessment row in the [adopt tracker](adopt-tracker.md)). A tool output that overstates its own
check feeds that directly.

**The fix:** wording. For example, "imports and registers 2 tools (no tool
was called)", until item 2 exists.

### 2. A behavioural admission check for plugins

- **The change:** `plugin_write` takes an optional example call: a tool name,
  arguments, and something the result must contain. The sandbox makes that
  call.
- **The labels:**
  - **behaviour-tested:** the example call succeeded;
  - **structure only:** there was no example call;
  - **failed:** the call errored or the result didn't match, and the write is
    reverted as today.
- **Why it matters for #29:** the plugin micro-loop needs an admission check
  stronger than "it imports". This is the paper's reference-solution check,
  applied to Prax's own writes.

## Queue: agent-written case generators (#29's flywheel)

#278 generates the computation family by hand. The flywheel version:
- A proposer reads the failed *feedback* cases and writes a new *generator*
  for that failure class, not a single case.
- A generator is admitted only if all of these hold:
  - its cases pass both ways, executed: the correct answer passes and the
    slip fails, as in #278's tests;
  - **flake check:** the same answer gets the same grade twice;
  - **decontamination** against the private goldens, which the proposer
    never sees;
  - **calibration:** current Prax passes some of its cases and fails some;
  - **difficulty judged from outside the loop,** on a solver from another
    provider. That is the [AutoBenchmark](autobenchmark.md) adopt, and it
    answers the saturation that agent-built tasks drift into.
- **Human spot-review** remains. AutoBenchmark found human direction helped
  in proportion to its specificity.
- **Precondition:** the plugin admission check above, and the eval-isolation
  row, because a proposer with sandbox access must not reach the private
  goldens.

## Bank

- **Training one role erodes another in shared weights.** Solver RL alone
  drove the shared model's proposer validity from 86.8% to 22.4%. MASS's
  solver training cost it the verifiable coding benchmarks. When the GPU
  lane trains Prax's models, gate on every role the weights serve, not only
  the trained one.
- **Measure clarification by coverage, not frequency.**
  - Ask-F1, whether the questions cover the withheld information, doubled
    while the ask rate moved 6 points.
  - Prax's `INTENT_CLARIFICATION_ENABLED` was rejected on measured cost and
    correctness and then deleted ([flag audit](../guides/flag-audit.md)).
  - If clarification is ever revisited, the eval needs underspecified cases
    with a registry of what is missing, scored on whether the questions find
    it.
- **Harness over model, again.** The weakest proposer gained the most from
  the harness, and in their evaluation harness choice explained most of the
  gap to model-card scores.

## Don't adopt

- **The RL training of proposer and solver.** It is a GPU job, on a
  terminal-task domain that isn't Prax's product. It also needs a Harbor-scale
  environment fleet.
- **Self-graded task review.** Grading a task with the model that wrote it is
  the homogeneous loop #29 keeps out.
